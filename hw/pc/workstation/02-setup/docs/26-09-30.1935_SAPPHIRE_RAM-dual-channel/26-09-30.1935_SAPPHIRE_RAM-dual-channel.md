| # | Method | Result | Verdict |
|---|---|---|---|
| 1.1 | `dmidecode -t memory`: slot assignment | module 1: `P0 CHANNEL A`, module 2: `P0 CHANNEL B` | ✅ each module in a different channel |

## 2. Theoretical values (the criterion)

| # | Configuration | Calculation | Maximum |
|---|---|---|---|
| 2.1 | DDR5-4800, 1 channel (64-bit) | 4,800 MT/s × 8 B | **38.4 GB/s** |
| 2.2 | DDR5-4800, 2 channels | 2 × 38.4 GB/s | **76.8 GB/s** |

2.3. Criterion: multi-threaded bandwidth **> 38.4 GB/s** means one channel physically cannot deliver it, so dual-channel is proven. Real-world results are typically ~60–70 % of the theoretical maximum.

### 4.2 `mbw` (single thread, 1 GiB)

File: `26-09-30.1935_SAPPHIRE_ram-30-mbw.txt`. MEMCPY 18.0 GB/s, DUMB 26.5 GB/s, MCBLOCK 24.6 GB/s. Plausible, but it **proves nothing about dual-channel**: one core can't saturate even one channel.

### 4.3 Invalid numbers

4.3.1. **`sysbench` read** reaches up to 188 GB/s, above the 76.8 GB/s theoretical maximum, so its read mode overstates bandwidth (a known property of that mode). Not used. Writes can't be inflated this way: data written to 512 MB blocks has to actually reach RAM.

4.3.2. **First run with 1 MB blocks** (`…-20-sysbench-1M-cache-INVALID.txt`): the block fits in cache, so results of up to 709 GB/s measure the cache, not RAM. Kept only for completeness.

## 8. Q&A: is DDR5-4800 fast enough, given the platform supports up to 5600? (2026-09-30)

8.1. **Short answer: yes.** For the planned work the difference is a few percent or not measurable. This confirms the decision made before purchase ([RAM candidate table, Q&A 6.2](../../../01-before.order/SAPPHIRE/SAPPHIRE_EdgeAI_370/RAM/26-09-26.2057_SAPPHIRE370_RAM-tabulka-kandidatu.md)); section 8 only adds the measured number.

| # | Item | DDR5-4800 (installed) | DDR5-5600 (platform max) | Difference |
|---|---|---:|---:|---|
| 8.2 | Theoretical bandwidth, dual-channel | 76.8 GB/s | 89.6 GB/s | +17 % for 5600 (upper bound) |
| 8.3 | Latency (2000 × CL / speed) | 16.7 ns (CL40) | 16.4 ns (CL46) | practically the same |
| 8.4 | Measured write bandwidth, 12 threads | 45.3 GB/s (59 % of theoretical) | not measured | in the usual 60–70 % range |

8.5. Where the speed does **not** matter: development, Docker, compiling, Claude Code, browser — limited by CPU, cache and SSD; latency (what makes the system feel responsive) is the same for both. Video playback and OBS use fixed encoder/decoder blocks.

8.6. Where it **would** matter (up to the 17 % upper bound):
8.6.1. Integrated graphics (Radeon 890M shares system RAM): roughly 10–15 % in heavy graphics load, mainly games — not a planned use.
8.6.2. Local LLM inference on CPU/iGPU/NPU: token generation speed scales almost linearly with memory bandwidth. **Only relevant if running local models becomes a real use case.**

8.7. Capacity matters more than speed here: 64 GB (58 GiB usable) is what enables VMs, Docker and many parallel tools without swapping. Replacing working 4800 modules with 5600 would cost ~20 k CZK for at most ~17 % in bandwidth-bound tasks only — not worth it.

8.8. Note: the reliable read-bandwidth number is still missing (the `sysbench` read mode overstates, 4.3.1). A better tool (e.g. a STREAM benchmark) would give the real read figure if ever needed; it doesn't change the conclusion.
