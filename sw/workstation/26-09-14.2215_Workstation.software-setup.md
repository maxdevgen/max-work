## ⚠ Zásadní upřesnění 2026-09-14: vývoj často dělá AI agent, ne uživatel sám

Vyšlo najevo, že vývoj na těchto projektech často probíhá tak, že kód píše **AI agent** (typicky Claude Code) – uživatel ho nemusí sám otevírat a psát/ladit ručně. To mění váhu celé předchozí úvahy o IDE (Visual Studio/VS Code/Rider):

- **AI agent pracuje čistě přes příkazovou řádku** – edituje soubory, spouští `dotnet build`/`dotnet test`/`dotnet run`, git příkazy. K tomu **není potřeba žádné GUI IDE, natož Windows** – funguje to identicky na Debianu jako kdekoli jinde. To je ostatně přesně to, co dělám já (Claude Code) i teď.
- **Role uživatele je spíš dohledová** – kontrola diffů/výstupů agenta, čtení kódu, příležitostné zásahy. Těžké interaktivní ladicí session (krokování přes desítky breakpointů) přestává být tou hlavní denní činností, jak jsme původně předpokládali.
- **Důsledek:** volba IDE (Visual Studio vs. VS Code vs. Rider) i otázka Windows VM se z "kritického blokujícího požadavku" mění spíš na "příležitostný nástroj pro to málo, co si uživatel odladí sám" – řádově nižší priorita, než jsme jí zatím dávali.

**To posiluje závěr, ke kterému už předchozí analýza (VS Code + C# Dev Kit, unit testy, .NET Core) směřovala:** Windows VM čím dál víc vypadá jako **zbytný náklad** (peníze i RAM), ne nutnost. Podrobná analýza níže zůstává jako podklad pro tu menšinu případů, kdy si uživatel bude chtít sám něco odladit ručně.

## ✅ Řešení příležitostné potřeby Windows: použít existující Dell, ne VM na novém stroji

⚠ doplněno 2026-09-14, rozhodnuto.

Padly dvě varianty, jak pokrýt "chtěl bych si Windows někdy zkušebně vyzkoušet": (a) neaktivovaná instalace Windows na novém stroji – funkčně skoro plnohodnotná, jen kosmetická omezení (vodoznak, nejde personalizace), ale je to myšlené jen jako dočasný stav, ne trvalé řešení; (b) **prostě použít Dell laptop**, na kterém už je legitimní, aktivovaný Windows 11 Pro.

**Zvoleno (b): pro tu příležitostnou potřebu se použije stávající Dell.** Je to nejjednodušší řešení ze všech – žádná nová licence, žádná VM, žádné rezervování RAM na novém stroji pro Windows. **Nový stroj tak zůstává čistě Debian**, bez Windows VM vůbec. Pokud by se v budoucnu ukázalo, že je Windows potřeba trvale/pravidelně (ne jen příležitostně), dá se tahle otázka znovu otevřít a řešit VM/novou licenci tehdy.

## OS architektura: Debian jako host, Windows jako VM (podrobně)

### Dual-boot vs. VM – v čem je rozdíl

- **Dual-boot** (zavrženo): Debian a Windows by byly dvě oddělené instalace vedle sebe na disku. Při startu počítače by se vybíralo JEDNO z nich (bootloader/GRUB) – běží vždy jen jedno, pro přepnutí je nutný restart. Nikdy neběží současně.
- **VM přístup (zvoleno):** Debian je jediný systém, co **bootuje přímo na hardwaru** (host). Windows se vůbec nespouští samostatně na holém železe – běží jako **virtuální stroj uvnitř Debianu** (přes KVM/QEMU nebo podobný nástroj), podobně jako běžný program. Debian mu "ukrojí" část CPU/RAM/disku. **Oba běží současně** – to je přesně ten scénář, kvůli kterému dává smysl 64 GB RAM (viz zdůvodnění v hardwarovém zadání).

### Jak plnohodnotný bude Windows ve VM

Pro hlavní účel (Visual Studio, kompilace .NET projektů, běžný vývoj) – **prakticky plnohodnotné**. Moderní virtualizace (KVM/QEMU s virtio ovladači) má u CPU/RAM/disk-intenzivní práce jen minimální režii (řádově jednotky procent) – kompilace ve VM poběží prakticky stejně rychle jako na holém železe.

Reálná omezení VM (pro úplnost, netýkají se přímo hlavního účelu):
- **Grafika/GPU** – VM standardně dostane jen základní virtuální grafiku, ne plný přístup k iGPU stroje. Pro psaní kódu/kompilaci nevadí, pro GPU-náročné úlohy (hry, GPU compute) by to bylo znatelně slabší bez speciálního (a ne vždy spolehlivého) nastavení.
- **Specifická USB zařízení** – hardwarový debugger apod. potřebuje ruční nastavení (passthrough), není automatické.
- **Spouštění** – Windows VM se po startu Debianu musí ještě samostatně nastartovat (vlastní boot čas), není to okamžité přepnutí.

### Windows licence

✅ prověřeno 2026-09-14: licenci ze stávajícího Dellu **nelze použít**. Ověřeno přímo na Dellu (`slmgr /dlv`) – jde o OEM licenci (`Product Key Channel: OEM:DM`), natrvalo vázanou na hardware Dellu; na jiném zařízení/VM by se neaktivovala. Vzdělávací (edukační) licenci taky nelze využít – nemá aktuální akademickou příslušnost (student/učitel/škola), která je pro ni podmínkou. **Musí se koupit nová retailová licence** – volba edice (Pro vs. Home) je otevřená, viz podsekce "Pro vs. Home" níže. **Náklad zatím není zahrnutý v hardwarovém rozpočtu ~25 000 Kč – je to položka navíc.**

### Jak se bude prakticky přepínat mezi Debianem a Windows

Závisí na tom, jestli bude u stroje připojená lokální obrazovka/klávesnice, nebo se k němu bude přistupovat vždy vzdáleně (⚠ **needěřeno, čeká na odpověď** – viz otevřené otázky níže):

- **Lokálně u stroje:** Windows VM se zobrazí jako **okno na Debian ploše** – spouští se a přepíná úplně jako jakákoli jiná aplikace (Alt+Tab), případně přes celou obrazovku. Pokročilejší varianta ("seamless mode") umí zobrazit jen okno konkrétní Windows aplikace (např. Visual Studia) přímo na Debian ploše bez viditelné Windows plochy okolo.
- **Vzdáleně (pravděpodobnější scénář vzhledem k 24/7 provozu a Claude Code):** Windows VM dostane na síti **vlastní IP adresu**, připojuje se k ní přímo přes **RDP** (vzdálená plocha) jako k samostatnému počítači. Debian se ovládá souběžně přes SSH/VNC jinou relací. "Přepínání" pak znamená přepínat mezi dvěma okny vzdálené plochy na zařízení, ze kterého se připojuješ (typicky Dell laptop) – jedna relace pro Debian, druhá pro Windows.

### Dell laptop jako "thin client" – jak přesně funguje využití výkonu nového stroje

Na dotaz "mohl bych používat svůj laptop a připojovat se na nový počítač, a využívat jeho prostředky pro práci?" – **ano, přesně tohle už je ten plánovaný model**, ať už přes RDP nebo AnyDesk/VNC (viz níže).

Princip vzdálené plochy (ať RDP, nebo AnyDesk/VNC): Dell laptop se stane čistě **"obrazovkou + klávesnicí"** (thin client) – posílá na nový stroj jen stisky kláves a pohyby myši, a zpátky dostává jen obraz (video stream). **Veškerý skutečný výpočet – kompilace, Visual Studio, Docker – běží fyzicky na novém výkonném stroji, ne na Dellu.** Specifikace Dellu (i5, 32 GB) jsou pro tu práci úplně jedno, protože Dell nic nepočítá, jen zobrazuje. Volba konkrétního nástroje (RDP vs. AnyDesk/VNC) na tenhle základní princip nemá vliv – liší se jen v detailech, viz tabulka níže.

### Pro vs. Home – volba edice Windows (otevřené rozhodnutí)

⚠ zatím **nerozhodnuto**.

| | Windows 11 Pro | Windows 11 Home + 3rd-party nástroj |
|---|---|---|
| Cena (elektronická licence) | 5 990 Kč (Alza) | ~3 006 Kč |
| Vzdálený přístup | nativní RDP (vestavěné) | AnyDesk / Chrome Remote Desktop / VNC (většina zdarma, nutno doinstalovat) |
| Integrace | o trochu lepší (sdílení schránky, tisk, disky, nižší latence v LAN) | funkčně srovnatelné u kvalitních nástrojů (AnyDesk), ale je to navíc software k údržbě |
| Ostatní Pro-only funkce (BitLocker, Hyper-V, Group Policy, doména) | ano | ne – ale pro tebe nejsou relevantní |
| Úspora | – | **~3 000 Kč** |

Základní princip (Dell jako thin client, výpočet běží na novém stroji) funguje **stejně dobře u obou variant** – volba je čistě o tom, jestli chceš nativní RDP (a zaplatit za Pro), nebo ušetřit ~3 000 Kč a použít externí nástroj jako AnyDesk.

## VS Code jako alternativa k Visual Studiu (možná nepotřebuješ Windows VM vůbec)

⚠ doplněno 2026-09-14.

### Dá se Visual Studio nainstalovat přímo na Debian?

**Ne.** Visual Studio (plná IDE, ne VS Code) na Linuxu/Debianu nativně nejde nainstalovat – Microsoft to potvrdil i pro rok 2026 (žádná linuxová verze v plánu). Zdroj: [Visual Studio Magazine – Confirmed, Finally, Again: No Visual Studio IDE for Linux/macOS](https://visualstudiomagazine.com/articles/2025/09/22/confirmed-finally-again-no-visual-studio-ide-for-linux-macos.aspx).

### Ale VS Code na Debianu umí otevřít klasické .sln i nové .slnx solution soubory

Ano, oba formáty. Potřebuješ k tomu rozšíření **C# Dev Kit** (od Microsoftu) – přidá do VS Code panel "Solution Explorer" (obdoba toho, co znáš z Visual Studia), s automatickou detekcí a otevřením .sln/.slnx souborů ve workspace, buildem i debugováním. Podporuje oba formáty stejně – jak starší **.sln**, tak nový XML-based **.slnx** (od .NET 10 je .slnx už výchozí formát pro `dotnet new sln`).

**Licenční poznámka:** C# Dev Kit je zdarma pro **individuální/nekomerční použití**, ale pro **firemní/profesionální nasazení** (větší firmy) formálně vyžaduje, aby uživatel byl krytý platnou licencí Visual Studia (stejná pravidla jako u VS Community edice – zdarma pro jednotlivce, open source, akademickou sféru; firmy nad 5 uživatelů/nad $1M ročního obratu potřebují placené VS předplatné). Pokud by se tohle používalo pracovně ve firmě, stojí za to si to ověřit u zaměstnavatele/licenčních podmínek.

**Praktický důsledek:** Pokud je hlavní důvod pro Windows právě "potřebuju otevřít .sln/.slnx a vyvíjet v C#/.NET", **VS Code + C# Dev Kit na Debianu by to možná zvládl bez Windows VM vůbec** – ušetřilo by to jak náklady na Windows licenci (~3 000–6 000 Kč), tak i tu RAM rezervovanou pro VM (~16–24 GB, viz zdůvodnění 64GB RAM).

**Zdroje:**
- [C# Dev Kit – Solution Explorer / opening solutions](https://code.visualstudio.com/docs/csharp/project-management)
- [Nový .slnx formát – Visual Studio Blog](https://devblogs.microsoft.com/visualstudio/new-simpler-solution-file-format/)
- [.slnx podpora v .NET CLI – .NET Blog](https://devblogs.microsoft.com/dotnet/introducing-slnx-support-dotnet-cli/)

### Ladění (debugging) – hlavní zbývající požadavek na Windows/VS

⚠ doplněno 2026-09-14, na dotaz "co ladění/debugging – to bez Visual Studia zvládnu?"

**Standardní ladění VS Code + C# Dev Kit zvládá plnohodnotně** – breakpointy (včetně podmíněných a "function breakpoints"), logpointy/tracepointy, watch okno, call stack, krokování (step into/over/out), exception breakpoints, hot reload, připojení k běžícímu procesu (attach). Není to odlehčená verze, je to postavené na stejném .NET debug enginu.

**Jedno reálné omezení, které jsme prověřili:** VS Code debugger **nepodporuje klasický .NET Framework**, jen .NET Core/.NET 5+. ✅ Vyřešeno – potvrzeno, že jde o **.NET Core**, takže se tohle omezení netýká.

**Upřesnění skutečné potřeby ladění (2026-09-14):** aplikace, na kterých pracuješ, jsou většinou dockerizované a nasazují se do Kubernetes – **lokálně se stejně nedají spouštět/ladit v plném běhu**, maximálně jde lokálně spustit a odladit **unit testy**. To zásadně zjednodušuje požadavek: VS Code + C# Dev Kit má **Test Explorer** s plnou podporou ladění jednotlivých testů (breakpointy v testu i v testovaném kódu) – to je přesně tenhle scénář, a je to dobře a spolehlivě podporované, žádné exotické omezení tu nehrozí. Reálné nasazené chování (Docker/Kubernetes) se stejně ladí jinak než lokálním debuggerem (logy, observabilita v clusteru), takže na tom nezáleží, jestli je to Windows VS nebo VS Code na Debianu.

**Průběžný závěr:** s potvrzeným .NET Core a debug workflow omezeným na unit testy vypadá čím dál pravděpodobněji, že **VS Code + C# Dev Kit na Debianu pokryje tvoje reálné potřeby bez Windows VM** – žádný z dosud prověřených bodů (solution soubory, debugging, .NET verze) tomu nebrání.

## JetBrains Rider – alternativní .NET IDE pro Linux

⚠ doplněno 2026-09-14.

**Dostupnost:** Rider běží **nativně na Linuxu** (včetně Debianu) – je to plně multiplatformní IDE (Windows/macOS/Linux), obecně považované za vyspělejší/plnohodnotnější .NET IDE než VS Code (blíž zkušenosti klasického Visual Studia).

**Cena:**

| Varianta | Cena | Podmínka |
|---|---|---|
| Nekomerční licence | **zdarma** | jen osobní/koníčkové projekty, open source, výuka – ne placená/firemní práce |
| Komerční licence | ~$16,90/měsíc (~$203/rok, cca **4 700–4 900 Kč/rok** dle kurzu) | pro placenou/pracovní činnost |

Nekomerční verze je plnohodnotná, ne omezená "lite" edice.

**Poznámka k volbě pro tebe:** je potřeba vědět, jestli je tahle nová práce na stroji **osobní/koníčková, nebo placená/firemní** – to rozhoduje, jestli je Rider zdarma, nebo ~4 800 Kč/rok. U VS Code + C# Dev Kit je licenční situace u firemního použití míň jasná (formální vazba na VS licenci), u Ridera je to naopak explicitní a jasná cena.

**Zdroje:**

- [Rider komerční ceny – přehled](https://www.trustradius.com/products/jetbrains-rider/pricing)
